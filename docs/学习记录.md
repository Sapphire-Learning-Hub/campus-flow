# CampusFlow 项目学习记录

## 一、使用 MSW 模拟后端 API

### 1. 遇到的问题

项目开发初期，真实后端接口还没有完全准备好，但登录、项目、任务、成员等页面已经需要开始联调。如果直接在组件中写死测试数据，虽然短期内能让页面显示出来，但后续切换到真实接口时需要大范围修改页面代码。

因此，我希望找到一种 Mock 方案，满足以下要求：

- 只在开发环境启用，生产环境不加载 Mock 代码；
- 能拦截真实的 `/api` 请求，而不是让页面直接读取本地数组；
- 页面和 Service 层不需要关心数据来自 Mock 还是真实后端；
- 能模拟延迟、失败、登录失效等真实网络情况；
- 将来接入真实后端时，尽量只修改环境配置。

### 2. 查阅的资料

- [MSW 官方文档](https://mswjs.io/docs/)：了解浏览器端请求拦截、Handler 和 Service Worker 的基本用法；
- MSW Browser Integration：确认开发环境中的启动方式；
- Vite 环境变量文档：了解如何通过 `import.meta.env` 控制 Mock 是否启用。

### 3. 最终方案

项目最终使用 MSW（Mock Service Worker）在浏览器网络层拦截请求。

目录结构如下：

```text
src/
├── api/mock/
│   ├── browser.ts      # 创建并导出 MSW Worker
│   ├── database.ts     # 保存模拟用户、项目、任务和成员数据
│   ├── handler.ts      # 汇总各领域 Handler
│   └── handlers/       # auth、projects、tasks、members、activities
├── services/           # 统一封装 API，页面不直接调用 Axios
```

在 `src/main.tsx` 中，只在开发环境并且显式开启 Mock 时启动 Worker：

```tsx
initializeAppSettings();

async function enableMocking() {
  if (import.meta.env.DEV && import.meta.env.VITE_USE_MOCK === "true") {
    const { worker } = await import("@/api/mock/browser.ts");

    await worker.start({
      onUnhandledRequest: "bypass",
      serviceWorker: {
        url: `${import.meta.env.BASE_URL}mockServiceWorker.js`,
      },
    });
  }
}

async function bootstrap() {
  await Promise.all([enableMocking(), i18nReady]);

  createRoot(document.getElementById("root")!).render(
    <StrictMode>
      <App />
    </StrictMode>,
  );
}

void bootstrap();
```

实际渲染时还会由 `StrictMode` 包裹 `<App />`。`initializeAppSettings()` 在 React 挂载前读取主题、品牌色、分页大小和默认视图，`i18nReady` 则保证翻译资源准备好后再渲染。

这里没有把 `mockServiceWorker.js` 写成固定的根路径，而是使用：

```ts
`${import.meta.env.BASE_URL}mockServiceWorker.js`
```

原因是项目将来可能部署在 `/campus-flow/` 这样的子路径下。如果直接写 `/mockServiceWorker.js`，浏览器会从网站根目录查找文件，部署后容易出现 404。

### 4. 为什么选择 MSW

**第一，页面调用方式和真实接口保持一致。**

页面仍然通过 Axios 请求 `/api/projects`、`/api/tasks`，MSW 只是在浏览器网络层把请求拦截下来。对页面来说，这就是一次正常的异步请求。

**第二，切换真实后端的成本较低。**

关闭 `VITE_USE_MOCK` 后，请求会直接发送到真实服务器。页面组件和 Service 函数通常不需要改动。

**第三，可以模拟真实请求状态。**

除了返回正常数据，还可以模拟：

- 网络延迟；
- 401 登录过期；
- 403 权限不足；
- 404 数据不存在；
- 400、409 等参数校验和冲突错误；
- 空列表和分页边界。

这些状态如果只靠组件中的静态数组，很难完整测试。

## 二、登录守卫与路由级认证

### 1. 遇到的问题

CampusFlow 中的工作台、项目管理、任务管理和个人设置都属于登录后页面。需要实现以下行为：

- 未登录用户访问受保护页面时，自动跳转到登录页；
- 登录成功后，返回用户原本想访问的地址；
- Token 失效时清除本地认证信息，并重新登录；
- 在认证结果出来之前，不渲染业务页面，避免页面内容短暂闪现。

一开始我想到的是在每个页面的 `useEffect` 中调用用户接口，然后根据结果执行 `navigate("/login")`。这种写法虽然能跳转，但认证检查发生在页面渲染之后，用户可能会先看到一瞬间的业务内容，而且每个页面都要重复写相同逻辑。

### 2. 查阅的资料

- [React Router: Data Loading](https://reactrouter.com/start/data/data-loading)
- [React Router: Route Object](https://reactrouter.com/start/data/route-object)
- [React Router: createBrowserRouter](https://api.reactrouter.com/v8/functions/react-router.createBrowserRouter.html)
- [React Router: redirect](https://reactrouter.com/api/functions/react-router.redirect.html)

### 3. 最终方案

最终使用 React Router Data Router 的 `loader` 作为登录守卫，并把它配置在所有受保护页面的父路由上。

```ts
export async function protectedRouter({ request }: LoaderFunctionArgs) {
  if (!getAccessToken()) {
    throw redirect(createLoginUrl(request));
  }

  try {
    return await getCurrentUser();
  } catch (error) {
    if (axios.isAxiosError(error) && error.response?.status === 401) {
      clearAccessToken();
      throw redirect(createLoginUrl(request));
    }

    throw error;
  }
}
```

守卫主要做两层判断：

1. 本地没有 Access Token 时，不再发送用户请求，直接进入登录页；
2. 本地有 Token 时，继续调用 `/auth/me` 验证 Token 是否有效，并获取当前用户信息。

### 4. 保留登录前地址

跳转登录页时，会把当前访问地址写入 `redirectTo`：

```ts
function createLoginUrl(request: Request) {
  const url = new URL(request.url);
  const redirectTo = `${url.pathname}${url.search}${url.hash}`;

  return `/login?redirectTo=${encodeURIComponent(redirectTo)}`;
}
```

登录成功后，登录页再读取 `redirectTo` 并跳转回去。

为了避免开放重定向，只允许站内路径：

```ts
function getInternalPath(value: unknown): string | undefined {
  return typeof value === "string" &&
    value.startsWith("/") &&
    !value.startsWith("//")
    ? value
    : undefined;
}
```

这里需要排除 `//example.com`，因为浏览器可能会把这种地址识别为协议相对 URL，从而跳转到外部网站。

### 5. 为什么采用 Loader

- **认证发生在渲染前。** Loader 未通过时，业务组件不会被创建，因此不会出现未授权内容闪烁。
- **父路由统一处理。** 所有子页面共享同一套认证逻辑，不需要逐页复制。
- **认证与用户数据可以合并。** `/auth/me` 不仅用于确认登录状态，还能直接把当前用户信息返回给布局和子页面。
- **错误边界更清晰。** 401 可以重定向登录页，其他错误则交给路由错误页面处理，而不是全部当作“未登录”。

## 三、复用路由 Loader 返回的用户数据

### 1. 遇到的问题

登录守卫已经通过 `getCurrentUser()` 获取了当前用户，但公共布局中的姓名、邮箱和头像仍然是硬编码内容。

如果布局再调用一次 `/auth/me`，同一次页面访问就会出现两次重复请求：

1. 路由 Loader 请求一次；
2. `AppLayout` 挂载后又请求一次。

这不仅浪费请求，还会让认证状态和页面用户状态分别维护，后续容易出现不一致。

### 2. 最终方案

为受保护父路由设置固定 ID：

```tsx
{
  id: "authenticated-app",
  loader: protectedRouter,
  element: <AppLayout />,
  children: [
    // 受保护子路由
  ],
}
```

然后在布局中使用 `useRouteLoaderData` 读取父路由 Loader 返回的数据：

```tsx
const loaderUser =
  useRouteLoaderData<AuthUser>("authenticated-app");
```

这样，路由守卫中获取到的用户对象可以直接提供给布局，不需要再次请求。

### 3. 为什么使用 `useRouteLoaderData`

`useLoaderData()` 只能读取当前路由自己的 Loader 数据，而 `AppLayout` 和具体业务页面可能处于不同层级。

`useRouteLoaderData("authenticated-app")` 可以通过路由 ID 精确读取指定父路由的数据，更适合共享当前用户、组织信息或全局权限等数据。

### 4. 兜底处理

为了提高健壮性，当 Loader 数据意外不存在时，布局保留一次恢复请求：

```tsx
const loaderUser =
  useRouteLoaderData<AuthUser>("authenticated-app");

const user = loaderUser ?? recoveredUser;

if (!user) {
  return <div className="app-loading">正在加载用户信息...</div>;
}
```

恢复请求使用 `useRef` 缓存同一个 Promise，避免 React Strict Mode 在开发环境中重复执行 Effect 时产生重复请求。

不过，这个恢复逻辑只是兜底，正常情况下仍应优先复用 Loader 数据。

## 四、国际化系统（i18n）

### 1. 遇到的问题

项目需要支持简体中文和英文，并且切换语言时不能刷新页面。国际化范围不仅包括普通文本，还包括：

- 页面标题、按钮、表单提示和错误信息；
- Ant Design 内置组件文案；
- Day.js 日期和时间格式；
- 浏览器标签标题等 HTML 元信息；
- 刷新页面后的语言状态恢复。

一开始我只考虑了在组件中使用 `t()` 替换文字，后来发现如果 Ant Design、日期库和页面元信息没有同步处理，页面会出现中英文混用。

### 2. 使用的工具

项目最终使用：

- `i18next`：国际化核心；
- `react-i18next`：让 React 组件能够使用翻译函数；
- `i18next-browser-languagedetector`：检测和保存语言；
- `i18next-http-backend`：从静态 JSON 文件加载翻译资源。

### 3. 初始化配置

```ts
i18next
  .use(initReactI18next)
  .use(LanguageDetector)
  .use(HttpBackend)
  .init({
    fallbackLng: "zh-CN",
    supportedLngs: ["zh-CN", "en"],
    detection: {
      order: ["querystring", "localStorage", "navigator", "htmlTag"],
      caches: ["localStorage"],
      lookupLocalStorage: "campus-flow:language",
    },
    backend: {
      loadPath: `${import.meta.env.BASE_URL}locales/{{lng}}/{{ns}}.json`,
    },
  });
```

语言检测顺序的含义是：

1. 如果 URL 查询参数中指定了语言，优先使用；
2. 否则读取用户上一次保存在 `localStorage` 中的选择；
3. 再根据浏览器语言判断；
4. 都无法确定时使用 HTML 的 `lang` 属性；
5. 最终使用 `fallbackLng` 兜底。

### 4. 与 Ant Design 联动

Ant Design 自带分页、日期选择器、空状态等内置文案，需要通过 `ConfigProvider` 切换 locale：

```tsx
const antdLocale =
  i18n.resolvedLanguage === "en" ? enUS : zhCN;

return (
  <ConfigProvider locale={antdLocale}>
    <RouterProvider router={router} />
  </ConfigProvider>
);
```

如果只翻译业务文案，不切换 `ConfigProvider`，就会出现页面按钮是英文、分页器仍然是中文的情况。

### 5. 与 Day.js 联动

语言变化时同步修改 Day.js locale：

```ts
i18next.on("languageChanged", (language) => {
  dayjs.locale(language === "zh-CN" ? "zh-cn" : "en");
});
```

这样日期格式、月份名称和相对时间才能与当前语言保持一致。

### 6. 首屏初始化

MSW 和 i18n 都需要异步初始化，因此在 React 首次渲染前一起等待：

```ts
await Promise.all([
  enableMocking(),
  i18nReady,
]);
```

这样可以避免应用先以翻译 key 或默认语言渲染，随后再突然切换成目标语言。

## 五、Ant Design Select 下拉框无法正常显示

### 1. 遇到的问题

项目中所有 Ant Design `<Select>` 都突然无法正常使用：

- 点击后下拉选项不显示；
- 下拉框出现后马上消失；
- Select 可以获取焦点，但弹出层无法稳定展开；
- DatePicker、Dropdown、Popover 等弹出层组件也出现类似现象。

因为问题同时出现在多个页面，最初很难判断是组件代码、表单状态还是 Ant Design 本身的问题。

### 2. 一开始的排查方向

我先后检查和尝试了以下内容：

- Select 的 `options` 是否正确；
- `Form.Item` 的 `name` 是否与表单字段对应；
- `initialValues` 是否与动态数据冲突；
- value 类型是否一致；
- 给 Select 增加 `key` 强制重新挂载；
- 手动传入 `open` 控制展开状态；
- 升级或降级 Ant Design 版本；
- 检查国际化切换是否导致组件重复渲染。

这些尝试都没有解决问题，也说明故障并不在某一个 Select 的业务逻辑中。

### 3. 真正原因

继续检查全局样式后，发现项目为了“减弱动画”，加入了类似规则：

```css
* {
  animation-duration: 0.01s !important;
  transition-duration: 0.01s !important;
}
```

这条规则影响了所有元素，也覆盖了 Ant Design 弹出层使用的动画。

Select、DatePicker、Dropdown、Modal 等组件的显示和销毁依赖 `rc-motion` 以及对应的 CSS 动画类。全局强制缩短动画后，弹出层的进入和退出状态被干扰，最终表现为无法展开或一闪而过。

### 4. 最终方案

删除对所有元素生效的动画覆盖，不再使用：

```css
* {
  animation-duration: 0s !important;
  transition-duration: 0s !important;
}
```

如果确实需要支持“减少动态效果”的无障碍设置，只针对自己编写的装饰动画：

```css
@media (prefers-reduced-motion: reduce) {
  .custom-decorative-animation {
    animation: none;
    transition: none;
  }
}
```

不要通过通配选择器修改组件库内部的动画行为。

### 5. 更有效的排查方式

这次问题让我发现，处理“多个组件同时失效”时，应该优先检查共享依赖，而不是逐个修改组件。

更高效的排查顺序是：

1. 在浏览器 DevTools 中找到弹出层 DOM；
2. 观察点击时 DOM 是否创建、是否立刻被移除；
3. 在 Styles 面板中逐条禁用可疑的全局 CSS；
4. 检查最近修改的 `base.css`、Reset 样式和主题样式；
5. 必要时使用 `git bisect` 找到引入问题的提交。

## 六、明暗主题与应用设置系统

### 1. 遇到的问题

个人设置页面需要支持：

- 浅色模式；
- 深色模式；
- 跟随系统；
- 自定义品牌色；
- 刷新后保留用户选择；
- 顶栏快速切换；
- Ant Design 和自定义页面样式同步变化。

一开始我只计划在 React State 中保存 `themeMode`，然后切换 Ant Design 的 `darkAlgorithm`。实际实现时发现，仅修改组件库主题并不够，自定义 CSS、HTML 属性和系统主题监听也必须同步。

### 2. 需要同时解决的状态

主题系统实际包含两个不同概念：

- **用户选择的模式**：`light`、`dark` 或 `system`；
- **最终生效的模式**：只能是 `light` 或 `dark`。

例如，用户选择 `system` 时，需要根据：

```ts
window.matchMedia("(prefers-color-scheme: dark)").matches
```

计算当前真正生效的是深色还是浅色。

### 3. 最终架构

项目将设置系统拆成三层。

#### 数据层：`src/services/preferences.ts`

负责：

- 从 `localStorage` 读取设置；
- 合并并保存部分设置；
- 把设置同步到 DOM；
- 通知订阅者数据发生变化。

```ts
export function saveAppSettings(
  patch: Partial<AppSettings>,
): AppSettings {
  const nextSettings = {
    ...getAppSettingsSnapshot(),
    ...patch,
  };

  currentSettings = nextSettings;

  localStorage.setItem(
    SETTINGS_STORAGE_KEY,
    JSON.stringify(nextSettings),
  );

  applyAppearance(nextSettings);
  notifyListeners();

  return nextSettings;
}
```

这里使用的是 listener 模式：

```ts
const listeners = new Set<() => void>();
```

它不依赖 React，因此在 `main.tsx`、普通工具函数和 React 组件中都可以操作同一份设置。

#### React 接入层：`SettingContext`

使用 `useSyncExternalStore` 订阅外部设置数据：

```tsx
const settings = useSyncExternalStore(
  subscribeToAppSettings,
  getAppSettingsSnapshot,
  getServerAppSettingsSnapshot,
);
```

`useSyncExternalStore` 的作用是把 React 外部的数据源安全接入 React 渲染过程。设置变化后，订阅它的组件会自动更新。

#### 应用层：Ant Design 与 CSS 变量

在 `App.tsx` 中，根据最终主题给 `ConfigProvider` 传入不同算法：

```tsx
const algorithm =
  resolvedTheme === "dark"
    ? theme.darkAlgorithm
    : theme.defaultAlgorithm;
```

在 CSS 中定义两套设计变量：

```css
:root {
  --text-primary: #1f2329;
  --surface: #ffffff;
  --layout-bg: #f5f7fa;
}

:root[data-theme="dark"] {
  --text-primary: #f2f3f5;
  --surface: #1f2329;
  --layout-bg: #141414;
}
```

`applyAppearance()` 则负责更新：

```ts
document.documentElement.dataset.theme = resolvedTheme;
```

### 4. 避免主题闪烁

如果等 React 渲染后再读取设置，页面可能先显示浅色，随后突然切换成深色。

因此，项目在 React 挂载前执行：

```ts
initializeAppSettings();
```

先把 `data-theme` 和品牌色写入 HTML，再开始渲染页面。

### 5. 跟随系统的监听

当用户选择 `system` 时，需要监听系统主题变化：

```ts
const mediaQuery =
  window.matchMedia("(prefers-color-scheme: dark)");

mediaQuery.addEventListener("change", handleSystemThemeChange);
```

用户手动选择 `light` 或 `dark` 后，则不应继续让系统主题覆盖用户选择。

### 6. 为什么没有只用 Context + useState

单纯使用 Context 和 `useState` 也能实现主题切换，但设置需要在 React 渲染之前读取，还需要被 React 外部代码访问。

使用外部 Store 的好处是：

- React 挂载前就能读取并应用设置；
- 不需要在多个地方维护状态副本；
- localStorage、DOM 和 React 共享同一个数据源；
- 订阅逻辑更集中。

## 七、统一封装页面异步数据加载

### 1. 遇到的问题

项目中的大部分页面都需要处理以下状态：

- 首次加载；
- 加载成功；
- 加载失败；
- 空数据；
- 用户主动重试；
- 后台刷新。

如果每个页面都重复编写 `useState` 和 `useEffect`，代码会越来越相似：

```tsx
const [data, setData] = useState<T>(initialData);
const [loading, setLoading] = useState(true);
const [error, setError] = useState<string>();

useEffect(() => {
  load()
    .then(setData)
    .catch(handleError)
    .finally(() => setLoading(false));
}, []);
```

这种写法看起来不复杂，但页面一多，就容易出现以下问题：

- 忘记捕获异常；
- 组件卸载后仍然更新状态；
- 多次请求返回顺序不一致；
- 首次加载和后台刷新使用同一个 `loading`，导致页面频繁闪烁；
- 每个页面的错误提示格式不统一。

### 2. 最终方案

抽取通用 Hook：`useAsyncPageData`。

```ts
interface AsyncPageDataResult<T> {
  data: T;
  setData: Dispatch<SetStateAction<T>>;
  loading: boolean;
  refreshing: boolean;
  error?: string;
  reload: () => Promise<void>;
  refresh: () => Promise<void>;
}
```

页面只需要提供初始数据、加载函数和错误转换函数：

```tsx
const {
  data,
  loading,
  refreshing,
  error,
  reload,
} = useAsyncPageData({
  initialData: [],
  load: () => listProjects(filters),
  getErrorMessage: getApiErrorMessage,
});
```

### 3. `loading` 和 `refreshing` 的区别

这两个状态看起来相似，但使用场景不同。

- `loading`：页面第一次进入时使用，通常显示骨架屏或整页加载状态；
- `refreshing`：页面已有旧数据时重新请求，保留当前内容，只在按钮或局部区域显示加载状态。

如果后台刷新也清空页面并显示整页 Loading，用户会感觉页面不断跳动，操作体验较差。

### 4. 组件卸载保护

请求发出后，用户可能立即离开页面。此时 Promise 仍可能完成，如果继续调用 `setState`，就会产生无效更新。

因此 Hook 中使用挂载标记：

```ts
const mountedRef = useRef(false);

useEffect(() => {
  mountedRef.current = true;

  return () => {
    mountedRef.current = false;
  };
}, []);
```

请求完成后先判断组件是否仍然挂载，再更新状态。

需要注意的是，这种方式只能避免无效的状态写入，并不会真正取消网络请求。后续如果需要完整取消请求，可以进一步接入 `AbortController`。

### 5. 请求竞态问题

当筛选条件快速变化时，可能同时发出多个请求：

1. 先请求条件 A；
2. 随后请求条件 B；
3. B 先返回并更新页面；
4. A 最后返回，反而覆盖了 B 的结果。

当前 Hook 已通过 `requestRef` 维护请求序号，并在组件仍挂载且请求序号匹配时才写入数据、错误和加载状态，因此已经具备“旧请求不能覆盖新请求”的保护。

### 6. `reload` 与 `refresh`

- `reload()`：适用于首次加载失败后的重试，会重新进入完整加载状态；
- `refresh()`：适用于新增、编辑、删除数据后的静默更新，保留原页面内容。

这种区分能让页面交互更加稳定，也能避免每次操作后都出现整页闪烁。


## 八、将本地假分页改为真实后端分页

### 1. 遇到的问题

项目列表和任务列表原先使用了类似下面的请求：

```ts
listProjects({ pageSize: 100 });
listTasks({ pageSize: 100 });
```

页面先一次性获取最多 100 条数据，然后再对这 100 条数据进行本地分页。

这种方式在数据较少时看不出问题，但它并不是真正的分页。当后端数据超过 100 条时，第 101 条之后的数据根本不会返回，页面却不会明显报错，只会表现为“数据好像就这么多”。

### 2. 本地分页和后端分页的区别

#### 原来的本地分页

```text
后端返回前 100 条
        ↓
前端保存 100 条
        ↓
前端使用 slice 切换页面
```

无论用户点击第几页，前端都不会重新请求服务器。

#### 正确的后端分页

```text
用户切换页码
        ↓
前端请求 page 和 pageSize
        ↓
后端查询对应范围的数据
        ↓
返回当前页 items 和完整 total
```

例如用户访问第 3 页、设置中的每页条数为 10 时，请求应类似：

```http
GET /api/projects?page=3&pageSize=10
```

后端返回：

```json
{
  "message": "success",
  "requestId": "request-id",
  "timestamp": "2026-08-03T00:00:00.000Z",
  "data": {
    "items": [],
    "page": 3,
    "pageSize": 20,
    "total": 136
  }
}
```

`items` 只包含当前页数据，`total` 表示满足当前查询条件的完整数据总量。

### 3. 统一分页类型

先定义统一的分页参数和返回类型：

```ts
export interface PaginationParams {
  page: number;
  pageSize: number;
}

export interface PaginatedResult<T> {
  items: T[];
  page: number;
  pageSize: number;
  total: number;
}
```

项目接口的参数继续扩展筛选条件：

```ts
export interface ListProjectsParams
  extends PaginationParams {
  keyword?: string;
  status?: ProjectStatus;
}
```

Service 层把分页参数原样传给后端：

```ts
export function listProjects(
  params: ListProjectsParams,
): Promise<PaginatedResult<Project>> {
  return unwrap(
    http.get<ApiResponse<PaginatedResult<Project>>>(
      "/projects",
      { params },
    ),
  );
}
```

### 4. 使用 URL 驱动分页状态

分页状态可以只放在组件 `useState` 中，但对于项目列表这类独立页面，更适合放进 URL 查询参数。

当前实现只把 `page` 放进 URL；`pageSize` 来自设置页保存的 `campus-flow:settings`，不会作为 URL 参数保存。例如：

```text
/projects?page=2&keyword=react
```

这样做有几个实际好处：

- 刷新页面后仍然停留在当前页；
- 浏览器前进、后退能够恢复分页状态；
- 复制链接后，其他人可以打开相同的列表位置；
- 分页、筛选和搜索状态有统一来源；
- 不容易出现组件状态与 URL 不一致。

React Router 中可以使用 `useSearchParams`：

```tsx
const [searchParams, setSearchParams] = useSearchParams();

const page = Math.max(
  1,
  Number(searchParams.get("page")) || 1,
);

const pageSize = appSettings.pageSize;
```

更新页码时，不直接修改列表数据，而是修改 URL；第 1 页会删除 `page` 参数，依靠默认值恢复：

```tsx
function handlePageChange(nextPage: number) {
  setSearchParams((previous) => {
    const next = new URLSearchParams(previous);

    if (nextPage === 1) next.delete("page");
    else next.set("page", String(nextPage));

    return next;
  });
}
```

URL 变化后，请求参数随之变化，再重新请求后端。


## 九、前端测试

### 1. 为什么要写测试

前端测试用于验证页面功能是否符合预期。

它关注的不是组件内部使用了多少个 `useState`，而是用户执行操作后，页面是否显示了正确结果。例如：

- 点击按钮后是否触发对应操作；
- 表单输入错误时是否显示提示；
- 接口成功后是否展示数据；
- 接口失败后是否显示错误状态；
- 切换分页后是否请求并展示下一页数据。

### 2. 使用的测试工具

项目中主要使用以下工具：

- **Vitest**：运行测试、组织测试用例、执行断言。
- **React Testing Library**：渲染 React 组件并查询页面元素。
- **user-event**：模拟用户点击、输入和键盘操作。
- **jest-dom**：提供 DOM 专用断言。
- **MSW**：拦截接口请求并返回可控制的测试数据。
- **Playwright**：在真实浏览器中进行端到端测试。


### 3. 测试初始化文件

创建 `src/test/setup.ts`：

```typescript
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(() => {
  cleanup();
});
```

其中：

- `jest-dom/vitest` 给 `expect` 增加 DOM 断言；
- `cleanup()` 会卸载测试中渲染的组件；
- `afterEach()` 表示每个测试执行结束后进行清理。

这样可以避免上一个测试留下的 DOM 影响后续测试。

------

### 4. 测试代码的基本结构

```typescript
describe("功能名称", () => {
  it("应该完成某个具体行为", () => {
    expect(实际结果).toBe(预期结果);
  });
});
```

三部分的作用分别是：

- `describe`：将同一功能的测试放在一个分组中；
- `it` 或 `test`：描述一个具体测试场景；
- `expect`：断言实际结果是否符合预期。

例如：

```typescript
import { describe, expect, it } from "vitest";

describe("加法函数", () => {
  it("两个数字相加后返回正确结果", () => {
    expect(1 + 2).toBe(3);
  });
});
```

------

### 5. 断言

断言是测试中的判断标准，基本格式为：

```typescript
expect(实际值).匹配器(预期值);
```

常用断言包括：

```typescript
expect(value).toBe(expected);
expect(object).toEqual(expected);
expect(value).toBeUndefined();
expect(value).toBeNull();
expect(text).toContain("关键词");

expect(element).toBeInTheDocument();
expect(button).toBeDisabled();
expect(input).toHaveValue("CampusFlow");

expect(mockFn).toHaveBeenCalled();
expect(mockFn).toHaveBeenCalledWith(argument);
```

`toBe` 适合比较数字、字符串和布尔值，`toEqual` 更适合比较对象和数组的内容。

### 6. 测试原则

编写测试时应注意：

1. 每个测试应该能够独立运行；
2. 测试之间不能共享未清理的数据；
3. 不要使用固定延迟等待页面更新；
4. 不要把所有依赖都 Mock 掉；
5. 优先验证用户能够看到的结果；
6. 测试名称应清楚描述业务行为；
7. 除正常情况外，还要考虑空数据、请求失败和边界情况。
